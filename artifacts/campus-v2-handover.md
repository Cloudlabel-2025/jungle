## Implemented changes

- Individual account password sign-in alongside explicitly enabled simulation access. Password hashes live in a separate collection, use salted scrypt, and are never included in state. Five failed attempts lock a provisioned account for 15 minutes. Inactive accounts are denied sign-in and authenticated APIs. Existing eight-hour signed HttpOnly sessions and origin checks apply. There are no default passwords or public registration.
- Configurable cohort support calendar: IANA timezone, eight-hour window, working weekdays, holidays. There is deliberately no inferred college calendar. CC must configure it before assignment. Existing attendance/infraction rules retain their frozen IST behaviour; changing those requires the outstanding rules decision.
- Private tickets with exactly the three frozen umbrellas. Students submit without categorisation; CC classifies, corrects with reasons, and assigns. Team peers cannot read another student's tickets. The single Mission Commander sees only currently assigned tickets; CC handles triage and escalation.
- Append-only support events record categories, owners, states, acknowledgements, substantive responses, interventions, attempts, recovery verification and escalation. Assignment, ticket updates and their events commit in one MongoDB transaction.
- First-response deadline is calculated from 60 configured working minutes at initial assignment. Unassigned elapsed wait is separate. Calendar snapshots, owner legs, first response, breaches and deadlines survive reassignment and reopening. Acknowledgement does not stop the SLA. Working-minute balance is derived from the preserved calendar. Breaches escalate on authenticated reads or mutations; there is no independent notification scheduler.
- All INT01–INT06 human intervention records support approving actor, performer, manual planned/actual times, guidance, outcome and evidence reference. MC/CC performer roles are validated for the four role-specific routes. Audio and email are evidence references to human activity; the app does not send email, record/upload audio, or generate speech.
- Success/failure attempts, evidence, explicit recovery verification, technical issue linkage and recurrence references. Resolution requires a verified successful attempt. Tickets already link to team tasks; journals can link only to the submitting student's own support ticket. Stable IDs can be reused in assessments and exported evidence.
- CC drafts cases only from resolved tickets with unsuccessful attempts and verified successful recovery. A draft requires cause, both approaches, applicability, prerequisites, redaction evidence and validation evidence. Explicit human redaction and resolution confirmation precede publication. Corrections return to draft; withdrawal removes access. Version history and raw sources remain separate. Learners search only published cohort cases; source ticket IDs, redaction notes and private validation evidence are excluded from public case payloads.
- CC publishes a versioned unfamiliar challenge for every student. Students submit one narrative baseline including exposure, activity, help used and reflection; command adds observable reasoning and narrative comments. There are no numeric baseline fields. Week-1 ranking payloads are empty and the interface explains why rankings are paused.
- MC proposes separate growth narratives and a 40/20/25/15 rubric. Evidence IDs must belong to the student; ticket evidence must be assigned to the proposing MC. Unobserved dimensions are null and prevent a total score. Reports require an explicit complexity/opportunity comparison, CC validation and allow student corrections. Help seeking incurs no new penalty. Reports explain that pathways are hypotheses, not employment guarantees.
- New daily trophy awards cap at 50. Existing balances and historical ledgers are preserved. Gamer roster/leaderboard payloads are team scoped; energy and clearance records are personal. The earlier global roster exposed other-team scores and has been corrected.
- CC support operations show backlog, breaches, escalations, umbrella counts, attempt outcomes and published cases; private JSON export includes the support evidence chain, case versions and governance events.

## Deployment and operator SOP

1. Back up the configured MongoDB replica set before deploying. `node --env-file-if-exists=.env.local scripts/backup-verify.mjs <absolute-private-backup-path>` writes a new backup (never overwrites) and verifies a restore into a disposable database. Keep the backup outside source control; use your deployment provider's encrypted scheduled backups for production.
2. Build and run `node --env-file-if-exists=.env.local scripts/migrate-v2.mjs`. This additive, repeatable migration creates integrity indexes and records its version without resetting rewards, journals, teams, or college configuration. Seed only when needed with the existing seed command.
3. Provision existing accounts with `node --env-file-if-exists=.env.local scripts/provision-account.mjs`. Supply a JSON object containing `email` and a unique 8–256-character `password` through secure stdin, not command arguments or checked-in files. Supply an explicit boolean `active` to enable/disable an account; a status-only update does not require a password. There is no default password. Reprovisioning a password resets the account lock. Public registration, automated recovery and MFA are not included.
4. In production set a random `SESSION_SECRET`, the exact HTTPS `APP_ORIGIN`, a replica-set `MONGODB_URI` and `DEMO_MODE=false`. Start with `npm start`. Give each institution a separate deployment/database under the current single-college, single-`alpha`-cohort architecture. This is not a general multi-tenant SaaS implementation.
5. CC → Expedition setup → Working calendar: enter the approved timezone, start time, weekdays and holidays. The window is eight hours. Existing assigned tickets retain their original calendar/deadline if configuration changes. Publish the discovery prompt separately; all students see it in Before You Board. Existing submitted baselines preserve their original prompt version.
6. CC → Council overview → Help Desk: monitor unassigned elapsed wait, classify, add tags/reason, assign a human owner. Corrections and reassignment require reasons. The one-hour obligation begins only with initial assignment.
7. MC → Dashboard/Coaching: acknowledge separately from a substantive response, give guidance or a concrete scheduled next action, record human intervention/evidence, record failures as well as successes, verify recovery, then resolve. Reopening preserves the original first-response record. Breaches remain visible after response and reassignment.
8. CC → Knowledge Library: draft a redacted case from a resolved ticket, verify failed/successful attempt evidence, confirm redaction and resolution, publish. To correct, return it to draft and review again; withdraw misleading guidance. All authorized CC users currently have publishing authority, matching the role-level brief; finer named-authority policy remains open.
9. MC proposes growth using student-owned IDs and a comparison of task complexity/opportunity. CC validates it; the student sees the validated report and can request correction. Use null for unobserved dimensions. A correction requires a revised proposal and new validation.
10. CC → Results → Support operations / private JSON export: reconcile tickets, issues, attempts, interventions, case versions and report evidence. Export is restricted to CC. The retention period and approved deletion process remain undecided; no destructive retention automation is enabled.

Rollback: take and verify a backup before release. Reverting the application preserves the additive collections; the previous app ignores them. Reverting code also reverts reward policy and privacy behaviour, so review those changes before rollback. Restoring into a live database requires a separately authorized operator procedure; the verification script never replaces the live database.

## Explicit limits

No fault injection, adaptive discovery, AI personality/suitability decisions, WORKVERSE scenario authoring, automated grading, voice synthesis, gift redemption, cross-institution games, calendar integration or external message delivery was added. Support notifications are in-app and poll driven. An operator must watch triage; unassigned-age alerts have no invented threshold. The current eight-hour calendar window must fit within one local day; overnight shifts need a separately agreed closed-day/holiday policy. There is no retention/delete policy, production scheduler, deployed backup service or claim of six-week pilot readiness. The existing certificate-clearance rule remains provisional pending exact certificate criteria. Email and voice evidence must be supplied by a human workflow.
