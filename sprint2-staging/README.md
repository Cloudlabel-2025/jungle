# Alumni Connect Sprint 2 staging candidate

**Team:** Fictional Team A. **Status:** Ready for CC review. Key 2 is pending.

This candidate is a QA implementation of the frozen Sprint 1 and Sprint 2 acceptance surface. It has its own React UI, Node API, and fresh MongoDB instance. It reads no application environment file and binds to localhost. The original learner starter and live CODEWILD cohort are outside this setup. Completion here demonstrates the candidate's behavior and provides no evidence of work performed by a real learner team.

## Reproduce the candidate

From the Jungle repository root with Node 22 and the root lockfile dependencies installed, run:

```powershell
node sprint2-staging/verify.mjs
node sprint2-staging/staging.mjs
```

The verifier prints the SHA-256 of the candidate source and dependency lockfile. Match it to [verification.log](verification.log) before signing off. The second command serves the local UI on **http://127.0.0.1:3112** and prints fresh fictional administrator and two alumnus credentials to your terminal. Keep that terminal private. MongoDB is started locally by the launcher, and first use may need the pinned MongoDB 7.0.24 binary. Stop with Ctrl+C. Relaunch to reset to 20 fictional records. Capture test evidence before shutdown. For a CC reviewer on a different machine, run the same source snapshot there or use an explicitly approved private staging environment and rerun the checks against it.

The review configuration supports India, the United States, and the United Kingdom. Country, course, skill, employment, phone, and postcode choices are review fixtures. CC must confirm they fit the intended exercise before approval. The file hash identifies source content. Record the approved archive digest or immutable commit alongside the verification hash at sign-off.

## CC acceptance checklist

Record **PASS, FAIL, or BLOCKED**, reviewer, timestamp, and evidence reference for every check against the same candidate. Capture the relevant screen, response status, or regression output without credentials or session cookies. The saved log records developer evidence. CC owns the independent verdict.

| Check | CC verification |
|---|---|
| S1-AC01 | Sign in as administrator and see the directory. |
| S1-AC02 | Verify the clean directory has 20 fictional records and corroborate it with the API response. |
| S1-AC03 | Open an individual record from the directory and confirm the profile matches. |
| S1-AC04 | Sign in as an alumnus and confirm the displayed profile belongs to that account. |
| S1-AC05 | Confirm the alumnus can access only their profile and that the API rejects a request for another fictional profile. |
| S1-AC06 | Confirm invalid credentials and unauthenticated profile requests are rejected. |
| S1-AC07 | Demonstrate the integrated UI, API, and database at the accepted test URL. Confirm whether CC accepts the local demonstration or requires a private shared URL. |
| S2-AC01 | Create a valid alumni record and verify its unique immutable ID is generated by the server. |
| S2-AC02 | Edit the record, reopen it after refresh and re-login, and compare the ID and timestamps. The ID and creation time stay stable and modification time advances on a real edit. |
| S2-AC03 | Try duplicate normalized email and nonblank registration numbers. Check that multiple blank registration numbers are allowed. |
| S2-AC04 | Review the supported values and exercise valid international names, real/nonfuture DOB, required fields, phone, country-specific postcode, controlled lists, graduation year, conditional employment details, and optional LinkedIn URL. |
| S2-AC05 | As an alumnus, verify Create/Edit are absent and that direct Create/Edit API requests are denied. |
| S2-AC06 | Rerun and attach evidence for all seven Sprint 1 checks on this exact candidate. |
| S2-AC07 | Repeat the browser Create/Edit journey and final smoke/regression on the accepted private test URL. Attach the build identity, logs, and reset evidence. |
